```
{"status": "sensor_init", "result": 1}
{"status": "sensor_state", "value": "NORMAL"}
[INFO]  Init success
[INFO]  Data callback registered
```

**关键：日志最后一行是 `[INFO] Data callback registered`，这是初始化完成的标志。**

**② 状态消息（JSON 行）**

```json
{"status": "sensor_init", "result": 1}
{"status": "sensor_state", "value": "NORMAL"}
```

**③ 测量数据（仅在触发"开始采集"后输出）**

```
RAW[0]: 0xAA418 (status=0x08)
RAW[1]: 0xAE4B0 (status=0x0A)
RAW[2]: 0xA7B4C (status=0x0B)
RAW[3]: 0xAA3FA (status=0x08)
...
```

- `RAW[n]` 中的 n 是循环计数（每轮从 0 开始）
- **三个通道循环：`n % 3 == 0` → PD3，`== 1` → PD2，`== 2` → PD1**
- 数值是 21 位 AD 原始值（十六进制）
- 每轮 FIFO 排空后输出 `[INFO] === DRAIN FIFO END: 42 entries, 0 samples ===`

### 2.2 启动命令（已通过抓包确认）

用 Device Monitoring Studio 抓取 PS01Tool 与传感器之间的实际通信，得到：

**PS01Tool 发送的 TX 数据（十六进制）：**

```
67 6E 73 74 0D 0A          → 即 ASCII "gnst\r\n"（启动采集）
67 6E 65 64 0D 0A          → 即 ASCII "gned\r\n"（停止采集）
```

**传感器对 `gnst\r\n` 的响应：**

```
[INFO]  AS7150 measurement started
~measurement started~
[INFO]  === DRAIN FIFO START ===
RAW[0]: 0xAA418 (status=0x08)
...
```

> 说明：`gnst` = "generate start"，`gned` = "generate end"，是厂商自定义命令。

## 三、正常工作的部分（已验证）

### 3.1 Windows + PS01Tool + CH340 —— ✅ 完全正常

在 Windows 电脑上：

## 四、故障现象（核心问题）

### 4.1 现象描述

**在 K1 上发送启动命令 `gnst\r\n`，传感器无任何响应：**

- 不输出 `~measurement started~`
- 不输出任何 `RAW[...]` 数据
- 也没有错误信息

```bash
$ printf 'gnst\r\n' > /dev/ttyUSB0
$ timeout 3 cat /dev/ttyUSB0 | tail -30
（无任何输出）
```

**在 Windows 上用 pyserial 发送同样字节，同样无响应。**

### 4.2 关键矛盾

**同一台 Windows 电脑、同一个 CH340、同一个 COM11、同一串字节 `67 6E 73 74 0D 0A`：**

| 发送方 | 结果 |
|---|---|
| **PS01Tool.exe**（厂商上位机，内部也是 pyserial） | ✅ **成功**，传感器开始输出 RAW 数据 |
| **自己写的 pyserial 脚本** | ❌ **失败**，传感器无任何响应 |

**这是整个问题的核心，也是最令人困惑的地方。**

## 五、已尝试并排除的排查项

### 5.1 命令格式变体（全部失败）

| 命令 | 结果 |
|---|---|
| `gnst\r\n`（6 字节） | ❌ |
| `gnst\n`（5 字节） | ❌ |
| `gnst\r`（5 字节） | ❌ |
| `gnst`（4 字节，无结尾） | ❌ |

### 5.2 DTR/RTS 电平组合（全部失败）

| DTR | RTS | 结果 |
|---|---|---|
| 高 | 高 | ❌ |
| 低 | 低 | ❌ |
| 高 | 低 | ❌ |
| 低 | 高 | ❌ |

> 注：DTR=低时，传感器完全不输出初始化日志（连 RX 都没有），说明 DTR 控制着传感器复位/使能。

### 5.3 发送延迟（全部失败）

在检测到 `Data callback registered` 后，分别延迟 **0 / 0.5 / 1 / 2 / 3 / 5 秒**再发送命令 —— 全部无响应。

也尝试过**手动触发**（程序停下来等人按 Enter，可任意延迟数十秒）—— 失败。

### 5.4 重试策略（全部失败）

| 策略 | 结果 |
|---|---|
| 连发 2 次，间隔 0.1 秒 | ❌ |
| 连发 2 次，间隔 0.2 秒 | ❌ |
| 连发 3 次，间隔 0.1 秒 | ❌ |
| 连发 5 次，间隔 0.5 秒 | ❌ |
| 先发 `gned\r\n`，再发 `gnst\r\n` | ❌ |

> 依据：Device Monitoring Studio 日志里 `gnst` 出现了 2 次，中间夹着约 2.4KB 的 RX 数据（约 0.2 秒），推测 PS01Tool 可能连发两次。但实测无效。

### 5.5 缓冲区处理（失败）

| 处理 | 结果 |
|---|---|
| 发送前 `reset_input_buffer()` | ❌ |
| 发送后 `flush()` | ❌ |

### 5.6 多线程架构（失败）

PS01Tool 是 GUI 程序，有独立的后台读取线程（`SerialWorker.run`）持续轮询读取串口。为复现该架构，专门写了**双线程脚本**：

- 线程 A：`while True: if in_waiting: read()`，每 2ms 轮询，永不停止
- 主线程：等初始化 → 发送命令 → 监控响应

**结果：仍然失败。**

### 5.7 跨平台验证（失败）

| 平台 | 结果 |
|---|---|
| Windows + Python 3.14.2 + pyserial 3.5 | ❌ |
| K1 Linux + Python 3 + python3-serial 3.5 | ❌ |

**两个平台都失败，排除"Linux ch341 驱动问题"的假设。**

### 5.8 其他尝试

| 尝试 | 结果 |
|---|---|
| 更换 K1 的 USB 口（4 个口都试） | ❌ |
| 不同波特率 | 不适用（RX 在 115200 完全正常） |

## 七、PS01Tool 程序分析（逆向结果）

`PS01Tool.exe` 是 **PyInstaller 6.x 打包的 Python 3.9 程序**（含 PyQt5、pyqtgraph、numpy、scipy）。

### 7.1 从字节码中提取到的关键信息

**串口相关的方法名：**
- `SerialWorker.connect` / `SerialWorker.disconnect`
- `SerialWorker.send_text_command`
- `SerialWorker.run`（读取线程）
- `SensorGUI.on_measure_toggle`（"开始采集"按钮的回调）

**`send_text_command` 附近的字符串常量包含：**
- `"cmd"`
- `"utf-8"`
- `"send_text_command"`

**`on_measure_toggle` 附近的字符串常量包含：**
- `"gnst"`
- `" (gnst)"`
- `" (gned)"`
- 中文界面提示：`"发送开始命令失败"`、`"发送命令失败"`、`"采集已开启 (gnst)"`、`"采集已暂停 (gned)"`

**串口参数相关字符串：**
- 只有 `"timeout"` 和 `"Serial"`

## 九、补充信息

### 9.1 已验证的传感器引脚定义

| 传感器引脚 | 说明 | 在 CH340 上的接法 |
|---|---|---|
| `3V3` | 电源正极，3.3V | 接 CH340 的 `3V3` 脚 |
| `GND` | 电源地 | 接 CH340 的 `GND` 脚 |
| `TXD` | 传感器发送 | 接 CH340 的 `RXD` 脚 |
| `RXD` | 传感器接收 | 接 CH340 的 `TXD` 脚 |

### 9.2 传感器工作流程（依据 PS01Tool 的使用说明）

> 打开程序 → 点击刷新 → 使用默认配置（115200 8N1）→ 点击连接（设备进入 standby 模式）→ **点击"开始采集"** → 波形出现

### 9.3 K1 的 UART 资源（备选方案调研）

K1 SoC 有 uart0~uart9。当前设备树仅使能 `serial@d4017000`（uart0，调试串口），`/dev/ttyS0`、`/dev/ttyS2`、`/dev/ttyS10` 存在但对应硬件未确认。

从内核补丁查得的 40Pin 可用 UART 引脚：

| UART | TXD PAD | RXD PAD | 40Pin 物理脚 |
|---|---|---|---|
| uart5_3 | 70 | 71 | 脚 7 / 11 |
| uart8_2 | 75 | 76 | 脚 23 / 24 |
| uart9_2 | 72 | 73 | 脚 13 / 15 |
| uart4_3 | 33 | 34 | 脚 37 / 32 |

**若要走硬件 UART，需修改设备树使能对应 UART 并配置 pinctrl。**
