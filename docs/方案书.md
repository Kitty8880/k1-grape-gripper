## 摘要

本项目在进迭时空 K1 平台（MUSE Pi Pro 开发板）上实现了一台**多模态协同的智能抓取终端**。
用户通过语音下达"夹葡萄"的指令，终端在本地完成语音识别、视觉确认与力控抓取，
全程无需键盘、显示器或远程连接，上电即进入待命状态。

系统由三个感知—执行环路构成：

- **语音环路**：本地 SenseVoice 模型识别中文指令，解析为"抓取 / 停止 / 查询"三类意图；
- **视觉环路**：MUSE Pi Pro 的 MIPI 摄像头实时成像，HSV + 几何特征定位目标物体，
  并通过中心 ROI 约束抑制桌面杂物干扰；
- **力控环路**：双 PS01 光学力传感器贴装于夹爪两指，实时测量夹持力，
  以"力到位即停"的自适应控制完成夹取，并识别舵机堵转以判定硬件极限。

三个环路通过**交叉校验**耦合：语音给出"想要夹什么"（意图），视觉给出"实际看到什么"（事实），
两者一致才执行抓取，不一致则拒绝并提示。这使系统具备真正的多模态协同能力，
而非简单的功能串接。

**在此之上，系统还实现了一个"具身抓取闭环"**（§3.5）：
摄像头不再只是"抓之前拍一张"，而是**以 3 fps 持续观测整个夹持过程**，
与压力传感器的 20 Hz 读数在每个节拍上融合，形成时序状态机：

```
采基线 → 闭合中 → 接触到 → 夹到了 → 已移到B
                    │         │
                    └→ 夹空    └→ 脱落
```

其中"夹到了"的判定是**双模态逻辑与**：
压力传感器读数上升 **AND** 视觉检测到葡萄边缘被平板压平（轮廓直边占比上升），
两者缺一不判 —— 只有力上升可能是把葡萄推走了，只有边缘变化可能是光照错觉。
"抓取成功"则定义为**从 A 点移到 B 点**（预学目标位置 + 停稳确认），
而不只是"夹住了"。

**实测关键数据**（均为在真实硬件上测得）：

| 指标 | 实测值 |
|---|---|
| **说完话 → 夹爪开始动作** | **1.33 s**（VAD 优化后；优化前 4.3 s） |
| 语音识别推理耗时 | 1.37 s（RTF 0.82，音频 1.66 s） |
| 视觉拍照 + 识别（单帧） | 1.4 s（拍照约 1.0 s，识别 0.43 s） |
| **具身闭环视觉刷新率** | **3 fps**（133 ms/帧，全流程检测） |
| **夹持状态识别（三档）** | **90 %（27/30）**，其中"夹紧"100 % |
| **A→B 到达判定** | 实测成功（距 B 点 35~49 px，容差 50） |
| 力控抓取执行 | **21.8 s**（闭合 13~17 s + 验证 7 s，10 次统计） |
| 单次抓取端到端（旧流程） | **约 29 s** |
| 单次抓取端到端（具身流程） | **约 25 s**（含搬运到 B 点） |
| **视觉识别成功率** | **100 %（20 帧）** |
| **ASR 识别准确率** | **100 %（句/字/意图，各 20 次）** |
| **抓取成功率** | **100 %（10 次）** |
| 力传感器噪声（单点） | σ ≈ 2.65 N |
| 力传感器噪声（0.8 s 平均后） | σ ≈ 0.24 N |
| 双传感器平均降噪 | 31 % |
| 舵机可输出最大夹持力 | 1.2 ~ 1.4 N（堵转） |

**一个诚实且有价值的工程结论**：本项目原本以"防止夹坏物体"为核心安全目标。
实测发现当前舵机（MG996R，5 V 供电）的最大夹持力约 1.2~1.4 N，
**低于葡萄的破裂力（估计 3~10 N）**，因此在该硬件范围内"夹坏"并非真实风险。
真正的工程风险是**夹持力不足导致滑落**。
力感知的价值因此从"防止破坏"转移到"确认夹持成功、自适应物体尺寸、识别硬件极限"。

## 一、引言

### 1.1 项目背景

边缘 AI 终端是当前嵌入式领域的重要方向：算力下沉到设备侧，数据不出本地，
响应及时且隐私可控。进迭时空 K1 作为国产 RISC-V AI 芯片，集成了 8 核 CPU 与
2 TOPS 的 NPU，为这类应用提供了完整的硬件基础。

但把 AI 能力"用起来"与"用好"之间存在明显差距。真实终端面对的是：
光照变化、背景杂乱、麦克风噪声、机械间隙、传感器漂移 —— 这些工程问题在
论文和 demo 中往往被理想化。本项目选择一个**对物理交互精度要求很高**的场景
（抓取易损水果），正是为了把这些问题真实地暴露并解决。

### 1.2 问题定义

**任务**：机器人识别桌面上的葡萄，并用自制夹爪安全夹取。

这个看似简单的任务包含三个层次：

1. **感知层**：在杂乱的桌面环境中定位目标物体；
2. **理解层**：把用户的自然语言指令转化为可执行的任务；
3. **执行层**：控制机械结构在合适的力下夹住物体，既不打滑也不破坏。

三个层次分别对应三种 AI 能力（视觉、语音、控制），且必须**本地完成**。

### 1.3 设计目标与约束

| 类别 | 内容 |
|---|---|
| **功能目标** | 语音触发 → 视觉确认 → 力控抓取，全流程本地、无人干预 |
| **交互目标** | 无需键盘/显示器；说出指令即执行；异常时给出明确提示 |
| **硬件约束** | 舵机仅 1 路可用 PWM 引脚（GPIO_49）；夹爪由 3D 打印件 + 舵机组成 |
| **算力约束** | NPU 2 TOPS；语音模型为内存带宽瓶颈，NPU 加速无收益 |
| **安全约束** | 有损坏硬件的操作禁止；力上限、位置下限、堵转识别三重保护 |

### 1.4 方案总览

```
        用户说"夹葡萄"
              │
              ▼
   ┌──────────────────────┐
   │  ASR（SenseVoice）    │  意图 = 抓取
   │  本地 CPU 推理        │  期望物体 = 葡萄
   └──────────┬───────────┘
              │
              ▼
   ┌──────────────────────┐
   │  视觉（MIPI 摄像头）   │  实际看到 = 葡萄（置信度 0.95）
   │  HSV + ROI + 几何     │  位置 = (1116, 174) r=181px
   └──────────┬───────────┘
              │
      ┌───────┴────────┐
      │  交叉校验        │  一致 → 继续
      │  意图 vs 事实    │  不一致 → 拒绝执行
      └───────┬────────┘
              │
              ▼
   ┌──────────────────────┐
   │  力控抓取             │  力到位即停（自适应尺寸）
   │  双 PS01 + MG996R     │  堵转识别（硬件极限）
   └──────────┬───────────┘

        提出验证 → 成功/重试
```

## 二、系统设计

### 2.1 硬件架构

| 部件 | 型号/规格 | 连接方式 | 说明 |
|---|---|---|---|
| 主控 | MUSE Pi Pro（K1） | — | 8 核 RISC-V，2 TOPS NPU |
| 摄像头 | MIPI CSI（OV5647） | CSI 排线 | 1920×1080，固定焦距约 30 cm |
| 麦克风 | USB PnP Sound Device | USB | 单声道，44100 Hz |
| 力传感器 ×2 | PS01（ams OSRAM AS7150） | 2× USB-UART | 115200 8N1，实测 21 Hz/通道 |
| USB-UART ×1 | CH340 | USB | 传感器 A（左指） |
| USB-UART ×2 | PL2303 | USB | 传感器 B（右指） |
| 舵机 | MG996R | GPIO_49（物理引脚 22） | 独立 5 V 供电，共地 |
| 夹爪 | 3D 打印平行夹爪 | 舵机直连 | 行程约 0~100 mm |

**关键硬件约束（实测）**：

K1 设备树的 `pinctrl-single,gpio-range` 只把少数引脚配置为 GPIO。
在 40Pin 中，同时满足 `MUX_MODE0` 与 `PAD_3V_DS4`（3.3 V 电平）的**只有 GPIO_49**。
因此舵机 PWM 只能使用这一个引脚，无法增加第二路硬件 PWM 或物理按键输入。
系统也未使用 `pwmchip0/1`（`npwm=1` 且已被背光占用）。

> 这一约束直接决定了交互方式：**语音是唯一可行的输入通道**。

**两条路径的分工：**

| | **具身闭环（主路径）** | 旧路径（回退） |
|---|---|---|
| 视觉 | **连续 3 fps，全程观测** | 拍照一次 |

| 失败识别 | **脱落 / 夹空 当场判** | 事后发现滑移 |

**分层原则**：

- **库层不依赖应用层**，可单独测试（如 `sensor_test.py`、`servo_minimal.py`）；
- **标定工具与运行代码分离**，标定结果写入 `config.yaml`，运行时不需改代码；
- **配置驱动**：所有硬件参数、力策略、阈值都在 `config.yaml`，调整无需改代码。

### 2.3 多模态协同设计（核心）

**★ 本系统有**两层**多模态协同，主路径是第一层：**

| 层次 | 协同的模态 | 作用 | 在哪 |
|---|---|---|---|
| **① 夹持判定层（主）** | **压力传感器 × 视觉边缘几何** | 判"有没有夹到 / 夹稳没有 / 到没到 B" | §3.5 |
| ② 任务决策层 | 语音意图 × 视觉事实 | 判"该不该抓、抓什么" | 本节下半 |

**★★ 为什么第二层不是重点**：任务决策层的校验只在**抓取前**起作用一次；
而第一层贯穿**整个夹持过程**，是"具身智能"真正的体现
（实时感知 → 实时判断 → 实时决策）。

#### 2.3.1 夹持判定层：力 × 边缘（主路径）

**设计要点：两个物理量做逻辑与，缺一不判。**

```
只靠力：力上升了 → 可能是把葡萄推走了，也可能是夹到了夹爪自身
只靠视觉：边缘变直了 → 可能是光照/视角变化造成的错觉
两者同时：两个独立物理量同时变化 → 判定成立
```

| 判定 | 力条件 | 视觉条件 | 确认拍数 |
|---|---|---|---|
| **接触到** | 力峰值 > 0.05 N | 扁平度最大涨幅 ≥ 0.015 | 连续 2 拍 |
| **夹到了** | 力峰值 ≥ 0.50 N | 扁平度最大涨幅 ≥ 0.015 | 连续 3 拍（锁存） |
| **已移到B** | 力 ≥ 0.15 N 且仍被夹持 | 距 B 点 ≤ 容差 且 停稳 | 连续 3 拍 |
| **脱落** | 力骤降 **或** 低于 0.03 N | 扁平度涨幅回落 / 葡萄消失 | 连续 4~5 拍 |
| **夹空** | — | 脉宽到下限 **且** 扁平度从未上升 | 连续 5 拍 |

**★ 所有判据都用"历史峰值 + 连续 N 拍确认"**，因为两个量都会冲高后回落
（实测力从 1.87 N 掉到 0.5 N 以下）。用当前值会因回落而永远判不出来。

**★★ 这里的"视觉"不是深度学习，而是边缘几何**：
葡萄被平板压紧时，边界由圆弧变成直线段，测"最长直边占轮廓周长的比例"
（扁平度），实测从 0.13 升到 0.18~0.20。详见 §3.2。

#### 2.3.2 任务决策层：语音 × 视觉（抓取前一次）

**设计要点：两个模态互为校验，而不是简单串接。**

```
只靠语音：用户说葡萄 → 系统按葡萄去夹 → 哪怕面前是鸡蛋
只靠视觉：说"夹那个东西" → 无法确定用户意图
两者结合：语音给意图，视觉给事实 → 不一致则拒绝
```

**校验逻辑**：

| 语音意图 | 视觉结果 | 系统行为 |
|---|---|---|
| 葡萄 | 葡萄（置信度 0.95） | ✅ 执行抓取 |
| 葡萄 | 未识别到目标 | ❌ 拒绝并提示（避免盲夹） |
| 葡萄 | 其他物体 | ❌ 拒绝并提示不一致 |
| 未指定 | 葡萄 | ✅ 按视觉结果执行 |
| 未指定 | 未识别 | ❌ 拒绝 |

**这一设计的意义**：它把"多模态"从"多个功能并列"提升为"多个模态共同决策"，
是系统智能性的直接体现。

## 三、技术实现

### 3.1 力感知子系统

#### 3.1.1 传感器接入与协议

PS01 是光学力传感器（ams OSRAM AS7150 光学前端），通过 UART 持续推送三路
光电二极管（PD1/PD2/PD3）的读数。

**协议要点（实测踩坑）**：

| 项目 | 说明 |
|---|---|
| 启动命令 | `D4 67 6E 73 74 0D 0A`（`\xd4gnst\r\n`，0xD4 为唤醒字节） |
| **启动时序** | 必须**等初始化日志打完**（约 50 行，末行为 `Data callback registered`）再发启动命令，否则命令被静默丢弃 |
| 数据格式 | `RAW[<idx>]: 0x<hex> (status=0x<hex>)`，`idx%3` → 0:PD3 / 1:PD2 / 2:PD1 |
| **有效更新率** | 标称 160 Hz 是**三路共享**，单路实测仅 **21 Hz** |

> **这个 21 Hz 是后续所有设计的物理前提** —— 它意味着无法做实时滑移检测
> （滑移振动在 10~100 Hz），也无法靠快速采样降噪。

**两只传感器的启动行为不同（实测）**：

| 传感器 | USB-UART 芯片 | 打开时行为 |
|---|---|---|
| A（左指） | CH340 | 自动打印约 50 行初始化日志 |
| B（右指） | PL2303 | **一行都没有**，直接等启动命令 |

因此软件不能用"有没有看到初始化日志"判断成败，改为用"有没有数据"作为最终判据。

#### 3.1.2 标定方法

**力标定**（已知质量法）：用一个 258 g 的牛奶盒作为已知载荷。

```
空载读数     683,457 计数
加载 2.53 N  687,413 计数
灵敏度 = (687413 − 683457) / 2.53 = 1,564 计数/N
```

**零点必须重新标定**：传感器贴装到夹爪后，机械预压会改变零点。
实测某次零点漂移达 1,768 计数（= 1.13 N），导致"两指大开着就显示有受力"。

**★ 更关键的是：零点必须用中位数，不能用均值。**

PS01 会周期性冒出一个大尖峰（实测 A +11,300 计数、B +6,800 计数）。
30 次采样的**均值**被拉高约 1,900 计数（= 1.2 N），
而**中位数**不受孤立尖峰影响。改用中位数后，曲线第一次变干净。

#### 3.1.3 噪声特性实测

这是本项目最基础也最重要的测量数据：

| 平均窗口 | 噪声 σ（牛顿） | 折算为单点等效样本数 |
|---|---|---|
| 单次采样 | 2.65 | 1 |
| 0.25 s | 0.66 | ~5 |
| 0.8 s | 0.24 | ~17 |
| 2.0 s | 0.22 | ~42 |

**关键发现：噪声主要不是白噪声，而是低频漂移。**

窗口从 0.25 s 延长到 2.0 s（8 倍），σ 只从 0.66 降到 0.22（3 倍）。
若是纯白噪声，8 倍窗口应带来 √8 ≈ 2.83 倍的降噪 —— 实际接近但说明
仍存在不可平均的漂移成分。

**已排除的噪声来源**：

| 假设 | 验证方法 | 结论 |
|---|---|---|
| 环境光干扰 | 遮盖测试 | 读数无差异，排除 |
| 机械振动 | 加泡沫垫 | 读数无差异，排除 |
| 调度抖动 | `chrt -f 50` + governor=performance | 无改善 |
| 定时器精度 | `PR_SET_TIMERSLACK=1ns` | 无改善 |

#### 3.1.4 双传感器融合

| 信号 | 噪声 σ（计数） | 相对单只 A |
|---|---|---|
| 单只 A | 4,199 | 1.00× |
| 单只 B | 2,986 | 0.71× |
| **差分 A−B** | 4,421 | **1.05×** ❌ |
| **平均 (A+B)/2** | **2,896** | **0.69×** ✅ |

**两者的噪声相关系数只有 +0.279（弱相关）**，所以：

- **做差不能抵消噪声**（反而比单只还差）；
- **做平均能降噪 31%** —— 独立噪声在平均时互相抵消。

**物理依据**：对称夹持静止物体时，左右两侧法向力必然相等（牛顿第三定律），
两只传感器测的是同一个力学量，平均它们是合理的。

**因此控制环使用 `(A+B)/2`，安全判定使用 `max(A,B)`（保守），
偏心检测使用 `|A−B|`。**

#### 3.1.5 控制结构的四版演进

这是本项目投入最多、也最有价值的一段工程过程：

| 版本 | 做法 | 结果 |
|---|---|---|
| **v1** | 力闭环**收敛到目标值** | ❌ 被噪声欺骗：两指全开（900 µs）也报"力已到目标" |
| **v2** | 自动接触阈值 + 位置闭环 | ❌ 阈值算出 1.82 N，**超过硬上限 1.50 N**，逻辑死锁 |
| **v3** | 位置为主 + 力为安全上限 | ⚠️ 能夹住，但**只能夹一个尺寸** |
| **v4** | **力到位即停 + 堵转识别** | ✅ 自适应尺寸，且能识别硬件极限 |

**为什么 v1 不行，v4 可行**：

```
v1 判据：|力 − 目标| < 0.15N     ← 双边容差，噪声从两侧都能骗它
v4 判据：力 ≥ 目标，连续 2 次     ← 单边阈值，噪声只能造成一次孤立假触发
```

**判"有没有跨过阈值"比判"等不等于目标值"稳健得多 —— 这是关键区别。**

**v4 的完整控制流程**：

```
阶段① 快速探测：每步 10 µs，测力窗口 0.4 s
        直到力 ≥ 接触阈值（0.4 N）→ 转入精调

阶段② 慢速精调：步长自适应（2~12 µs，按观测到的力梯度调整）
        测力窗口 0.6 s，直到力 ≥ 目标力（连续 2 次）→ 停止

安全监控（全程）：
  · 力 > 硬上限（连续 2 次）    → 立即松开
  · 位置到达机械下限            → 转堵转判定
```

**自适应步长的依据**：不同葡萄的力—脉宽曲线斜率差异极大。

| 葡萄 | 斜率 | 后果 |
|---|---|---|
| 小而软 | 0.13 N/µs（陡） | 必须用小步长防过冲 |
| 大而硬 | 0.012 N/µs（缓） | 固定小步长会走 30 步、耗时 27 秒 |

按观测梯度自动在 2~12 µs 之间调节后，两种情况都能在 8~10 秒内完成。

#### 3.1.6 舵机堵转识别（创新点）

**问题**："脉宽 → 开口"的映射只在**空载**时成立。葡萄挡住夹爪时，
MG996R 扭矩不足就推不动，实际夹爪停在葡萄表面，而命令脉宽一直在减小。

**实测数据**：

```
780 µs  +0.748 N
770 µs  +0.706 N
760 µs  +0.717 N     脉宽走了 30 µs，力只变 0.05 N
750 µs  +0.758 N
```

**力进入平台期** —— 这不是"力不足"，而是**已经到舵机的物理极限**。

**判据**：

```
若 最近 3 步的力跨度 < 0.12 N（平台期）
    且 力 ≥ 最低要求   → 判定夹住（这就是最大夹持力）
    且 力 <  最低要求   → 判定太弱，物体太小/不在两指间
否则（力仍在变化）
    按常规阈值判定
```

**这个区分的价值**：避免了"目标力设得太高，控制环永远不收敛"的死循环
（实测踩过：目标 2.0 N，舵机上限 1.37 N，永远达不到，一路走到机械底）。

### 3.2 视觉子系统

#### 3.2.0 主路径：连续观测 + 边缘几何

**★ 视觉在新方案里有**两个任务**，主任务不是"找葡萄在哪"，而是"看夹持过程"：**

| 任务 | 帧率 | 方法 | 输出 |
|---|---|---|---|
| **① 夹持状态判定（主）** | **3 fps 持续** | **轮廓几何 → 扁平度** | 自由 / 贴住 / 夹紧 / 脱落 |
| ② 葡萄定位（辅助） | 同上，复用同一帧 | HSV 掩码 + 圆形度筛选 | 质心、宽度 |

**★★ 为什么用"轮廓几何"而不是深度学习或 Canny：**

```
葡萄被两指压平时，边界由「圆弧」变成「直线段」
  → 提取轮廓 → 多边形近似 → 量最长直边占周长的比例（扁平度）
  → 自由 0.13 → 夹紧 0.19（实测中位数）
```

| 候选方法 | 问题 |
|---|---|
| Canny / Sobel 梯度 | 实测该摄像头清晰度仅约 40（Laplacian），Canny 出来边缘是碎的，无法稳定量直边长度 |
| YOLOv8n 检测 | 只输出边界框，给不出"轮廓有多直"；而且遮挡一半就检不到 |
| **轮廓几何** | 颜色分割能得到**闭合**边界，多边形近似后直边清晰可测；**无需训练** |

**★★★ 实测准确率：三档（自由/贴住/夹紧）分类 **90 %（27/30）**，
其中"夹紧" **100 %** 可分。详细方法、阈值标定与失败分析见技术文档 §6.7。**

**关键的工程细节：**

- **必须做"现场基线"**：同一状态在不同来源下扁平度差别很大
  （存档照片 0.130 / 实时流 0.147 / 误锁黑色块时 0.259），
  所以判据用**相对基线的增量**，不用绝对阈值；
- **两套阈值**：捕获期严格（圆度 ≥0.60），跟踪期宽松（≥0.42）——
  葡萄被夹扁后圆度会掉下来，严格阈值会导致"夹紧后视觉丢失"；
- **拒收被画面边缘切掉的轮廓**：切边会产生假的直边，
  扁平度从 0.14 虚高到 0.28（踩过这个坑）。

#### 3.2.1 三种方案对比（定位用，非主任务）

项目先后实现并实测了三种**定位**方案：

| 方案 | 技术 | 是否用 AI | 实测性能 | 结论 |
|---|---|---|---|---|
| A | HSV 阈值 + 凸包几何 | ❌ 传统 CV | 90 ms/帧 | **定位采用**（可解释、无需训练） |
| B | YOLOv8n + int8 量化 | ✅ 深度学习 | **19.0 fps（52.7 ms）**，NPU | 验证可行，但 COCO 无"葡萄"类 |
| C | MobileNetV3 迁移学习 | ✅ 深度学习 | 训练中 | 数据已采集 280 张 |

**方案 B 的部署记录（技术价值高）**：

YOLOv8n 的量化 ONNX 模型在 K1 NPU 上运行，需注意**导入顺序**：

```python
import onnxruntime          # ← 必须先导入
import spacemit_ort         # ← 再导入，否则报 undefined symbol 错误
```

报错信息 `OSError: libspacemit_ep.so.2.0.3: undefined symbol: ...CreateProvider...`
具有误导性 —— 实际原因是导入顺序，而非库损坏。

#### 3.2.2 HSV 标定方法

**不能照抄网上的紫色区间**，必须按实际光照标定。
项目因此开发了 `vision_diag.py`：拍照后统计 H 通道直方图，输出推荐区间。

**标定结果（2026-11-02 实测）**：

| 品种 | H（色相） | S（饱和度） | V（亮度） | 结论 |
|---|---|---|---|---|
| **紫葡萄** | **140** | **33** | **39** | 深紫近黑 |
| **绿葡萄** | **28~33** | 高 | 中高 | 黄绿 |

**★ 一个关键发现：紫葡萄的 S 和 V 都很低（33 / 39）。**

常见的紫色区间写法是 `(125, 40, 40) - (170, 255, 255)`，要求 S≥40、V≥40 ——
**这个葡萄每一条都不满足，会被完全刷掉。**

正确的思路是"**深色 + 有一定色相**"，而不是"高饱和 + 高亮度"：

```python
"grape": [
    ((120, 15, 15), (180, 255, 130)),   # 深紫：V≤130 排除白桌面
    ((20, 45, 25), (50, 255, 225)),     # 绿：H 20~50
]
```

#### 3.2.3 误检修正（ROI + 最大面积选优）

**实测踩到的最严重问题是一次"成功"的误检：**

```
原逻辑：按圆度最高选优
结果：选中了【手指甲】(r=34, 圆度 0.90)，报告"葡萄 置信度 0.81"
而真正的葡萄 (r=62, 圆度 0.48) 被忽略
```

**原因**：手指甲又小又圆，圆度天然比葡萄高；桌面场景里深色/紫色物体太多
（胶带卷、键盘、手机、手），单纯靠颜色+形状无法区分。

**修正两条**：

1. **选优标准从"圆度最高"改为"面积最大"**（在 ROI 内）
2. **加中心 ROI 约束**：默认只接受画面 25%~85%（横向）与 15%~85%（纵向）内的候选

**修正后效果**：

```
✅ 看到葡萄   置信度 0.95   耗时 433ms
   #1 中心(1116,174) 半径 181px 圆度 0.97 面积 88614  ✅在ROI
```

**只剩一个候选，圆度 0.97，置信度 0.95。**

### 3.3 语音子系统

#### 3.3.1 本地部署

使用 SpacemiT 提供的 SenseVoice 量化模型（229 MB），完全本地推理。

**两个必须解决的工程问题**：

**① 采样率不匹配**

```
录音：44100 Hz
ASR 期望：16000 Hz
```

若直接把 44100 Hz 数据送入，ASR 会按 44100/16000 = 2.76 倍"放慢"来理解，
输出变成 `<|SAD|><|BGM|>` 这类垃圾标签。

**实测证据**：录 3.0 秒的"夹葡萄"，ASR 报"音频长度 8.320s"
（3.0 × 44100 / 16000 = 8.27）—— 数字完全吻合。

**解决**：录音后重采样到 16 kHz（或直接用 `arecord -D plughw` 让 ALSA 转换）。

**② 录音阻塞**

PyAudio 的 `stream.read()` 在 USB 音频缓冲区欠载时会**永久阻塞**，
`Ctrl+C` 也打不断（阻塞在 C 层）。实测在 1.3 秒处卡死。

**解决**：改用 `arecord` 子进程，用轮询输出文件大小显示进度，并加看门狗超时。

#### 3.3.2 唤醒词与意图解析

**关键设计决策：关键词匹配，而非要求用户说完整句子。**

实测发现"请帮我夹一个葡萄"这类长句在 VAD 下常被削掉开头
（实测只录到 0.864 s，被识别成"第二"）。因此：

```python
GRASP_WORDS = ("葡萄", "提子", "夹", "抓", "拿", "开始", "来一个")
STOP_WORDS  = ("停下", "停", "松开", "放开", "别夹", "停止")
```

**只要句子里出现"葡萄"就触发抓取** —— 大幅提高鲁棒性。
停止词优先判断，避免误触发。

### 3.5 具身抓取闭环（2026-11-07 新增）

**为什么需要它**：旧流程是**单帧快照** —— 抓取前拍一张照片定位，
然后闭眼完成整个夹持过程。但"夹住了没有 / 正在滑 / 已经掉了"是**随时间演化**的过程，
只看一瞬间判断不出来。

**做法**：让视觉持续观测（3 fps），与力传感（20 Hz）在每个节拍融合。

```
┌─ 视觉线程 3 fps ──────────────────────────┐
│  连续视频流 → 颜色分割 → 轮廓 → 扁平度      │
│  七帧中值稳定器（空间门限 + 时间中值）       │
└─────────────────┬─────────────────────────┘
                  ↓
┌─ 主循环 10 Hz ────────────────────────────┐
│  测力（0.35 s 窗中位数）→ 状态机 tick()     │
│  融合判据 → 状态事件 → 控制是否继续闭合      │
└─────────────────┬─────────────────────────┘
                  ↓
┌─ 网页实时预览（MJPEG，约 3% CPU）──────────┐
│  复用同一条视频流，画标注后推流              │
└───────────────────────────────────────────┘
```

**五种状态 + 两种失败：**

| 状态 | 判据 |
|---|---|
| 采基线 | 张开、未接触，实测扁平度基线（**用相对变化，不用绝对阈值**） |
| 闭合中 | 力 < 目标，脉宽逐步减小（每拍 2~4 µs） |
| **接触到** | 力峰值 > 0.05 N **且** 扁平度最大涨幅 ≥ 0.015（连续 2 拍） |
| **夹到了** | 力峰值 ≥ 0.50 N **且** 扁平度涨幅 ≥ 0.015（连续 3 拍后锁存） |
| **已移到B** | 距预学 B 点 ≤ 容差 **且** 停稳 **且** 仍被夹持 |
| 脱落 | 扁平度涨幅回落 **且** 力也低 / 力骤降 / 葡萄消失 |
| 夹空 | 脉宽到下限 **且** 扁平度从未上升（机械事实 + 视觉） |

**双模态融合是逻辑与，不是主辅：**

```
夹到了 = 力上升  AND  边缘变直
         └─ 只有力上升 → 可能把葡萄推走了
         └─ 只有边缘变直 → 可能是光照错觉
```

**所有判据都用"历史峰值 + 连续 N 拍确认"** ——
因为力和扁平度都会"冲高后回落"（实测力从 1.87 N 掉到 0.5 N 以下），
用当前值会因为回落而永远判不出来。

**A→B 判定需要预学**：把葡萄放到目标位置，运行 `--learn-b` 按回车记录，
存成**画面比例**（换分辨率不失效）；之后判"距 B 点 ≤ 容差 **且** 连续 3 拍几乎不动"。
只判位移不够 —— 位移分不出"到了 B"和"路过 B"。

**实测状态序列**（2026-11-07，语音触发，全程 25 s）：

```
🗣 听到：葡萄 → 意图 grasp  (ASR 1.31s → 说完共 1.33s)
[ 3.6s] 闭合中   扁平度 0.150
[ 8.2s] 接触到   +0.92N  涨幅 +0.0307
[ 9.2s] 夹到了   +1.29N  涨幅 +0.0307
[25.4s] 已移到B  距 B 点 35px ≤ 50px
```

**与旧流程的取舍**：具身流程用纯 CV（不调用 NPU），
因为 AI 核占用 ≈ 帧率 × 推理时间，而 CPU 上的边缘精测是 133 ms/帧，
提高帧率会让 CPU 超过 60 %。**这是有意识的资源取舍，详见技术文档 §11.7。**

**★ 优化后"说完 → 夹爪开始动"从 4.3 s 降到 **1.33 s**（VAD 静音 1.5→0.9 s、

### 4.2 优化措施

**已实施**：

| 措施 | 效果 |
|---|---|
| 力控改用**自适应步长**（按力梯度 2~12 µs） | 闭合阶段从 27 s 降到 13~17 s |
| **两阶段探测**（快速逼近 + 慢速精调） | 避免全程小步长的 60 s |
| 视觉**降采样 0.5 倍** | 1080p 全分辨率 700 ms → 90 ms |
| 中位数代替均值 | 消除尖峰导致的零点偏移 1.2 N |
| 双传感器平均 | 噪声降低 31% |
| **--fixed 固定时长录音** | 绕过 VAD 削句首问题 |

**计划实施**：

| 措施 | 预期效果 |
|---|---|
| **摄像头拍照与 ASR 推理并行**（流水线） | 响应延迟 3.8 s → **2 s 以内** |

| 减少力控探测步数（大物体预测起点） | 抓取 11 s → 6~8 s |

### 4.3 硬件利用率分析（含 NPU 说明）

**当前 NPU 占用：0%**

**为什么**：

| 任务 | 为什么不上 NPU |
|---|---|
| 语音识别（SenseVoice） | **内存带宽瓶颈**：实测 RTF 0.82（NPU）vs 0.81（CPU），NPU 无收益 |
| 视觉识别（HSV + 凸轮） | 不是神经网络，是 OpenCV 算子，跑在 CPU |
| 物体分类（MobileNetV3） | 单次推理 40 ms，一次抓取只需一次，CPU 已足够 |

**NPU 的合理用途（已在方案中规划）**：

**用 YOLOv8n（已实测 19 fps @ NPU）做并发的人手安全监控。**

- 后台线程持续推理，检测画面中是否有人手靠近
- 检测到人手 → 暂停抓取并语音提示
- **这是真实的持续 AI 负载**，而非为了凑指标

**报告中的诚实表述**：

> 语音与视觉均不适合 NPU（前者内存受限，后者单次推理）。
> 因此将 NPU 用于并发的持续任务 —— YOLOv8n 人手安全监控，
> 实测 19 fps，AI 核持续占用。这一选择同时增强了系统的安全性叙事。
