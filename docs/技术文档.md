## 1. 项目概述

### 1.1 任务

在一台 RISC-V 单板计算机（K1 MUSE Pi Pro）上，构建一套具备**多模态感知**能力的机器人抓取系统：
利用 AI 视觉识别葡萄目标，通过**力闭环控制**驱动机械夹爪，实现对葡萄的**无损抓取**（不破皮、不脱落）。

### 1.2 核心难点

一颗巨峰葡萄约 12 g，赤道直径 22 mm，**捏破它只需要 1~3 N 的力**。这意味着：

- 夹持力太小 → 摩擦不足 → 葡萄滑落
- 夹持力太大 → 超过果皮强度 → 葡萄破裂
- 力上升太快 → 冲击过冲 → 即使最终力合适也会压破

**这是一个典型的"力控精度"问题，而不是"力大小"问题。**

### 1.3 技术路线

| 维度 | 选择 | 说明 |
|---|---|---|
| **感知模态** | 视觉（CV）+ 语音（ASR） | 满足"至少两种模态"要求 |
| **推理位置** | 全部本板本地推理 | 满足"本地推理"要求 |
| **力感知方案** | PS01 光学力传感器 ×2 | 导师指定器件，非接触式光学测量 |
| **控制方案** | 力闭环 PI + 速率限幅 | 靠摩擦而非挤压实现稳定夹持 |
| **实施阶段** | 阶段一：力闭环；阶段二：视觉+机械臂 | 先攻克风险最高的环节 |

### 1.4 核心设计思想

> **不是"用力夹住"，而是"轻轻碰住，靠摩擦吊起来"。**

量化如下：

| 参数 | 数值 | 依据 |
|---|---|---|
| 目标夹持力 F\* | **0.8 N** | 葡萄破裂力的 1/3，留 3 倍安全裕度 |
| 单侧硅胶垫摩擦系数 μ | ≈1.0 | 邵氏 A30 硅胶对葡萄表皮 |
| 双侧总摩擦力 | 0.8 N × 2 × 1.0 = **1.6 N** | ≫ 葡萄自重 0.12 N |
| 安全系数 | **13 倍** | 1.6 N / 0.12 N |

**结论**：只需要很小的力就能稳定夹持，因此控制系统应当追求**精密的力控制**而不是**大扭矩**。

### 2.3 夹爪状态机

```
  INIT ──▶ OPEN ──▶ APPROACH ──▶ CONTACT ──▶ RAMP ──▶ HOLD ──▶ RELEASE ──▶ DONE
                       │            │          │        │          │
                       └────────────┴──────────┴────────┴──────────┴──▶ ABORT
                                    （任一安全条件触发即转入 ABORT）
```

| 状态 | 动作 | 退出条件 |
|---|---|---|
| `INIT` | 硬件自检 | 传感器/舵机就绪 |
| `OPEN` | 夹爪张开到最大 | 到达开位 |
| `APPROACH` | 快速接近目标 | 检测到接触（F > 阈值） |
| `CONTACT` | 停止，确认接触 | 力稳定 |
| `RAMP` | **限速升力**至目标力 | F ≥ F\* |
| `HOLD` | 保持目标力 | 定时/外部指令 |
| `RELEASE` | 缓慢松开 | 到达开位 |
| `ABORT` | 立即卸力 | — |

## 4. 力传感器接入（PS01）

> **本章是本项目的核心技术成果之一。**
> 传感器无公开协议文档，通过反编译厂商上位机逆向出隐藏的通信协议，
> 最终实现 135 Hz 稳定数据采集。

### 4.1 传感器介绍

**PS01** 是由「ams OSRAM AS7150 光学力传感模拟前端（AFE）+ 红外 LED + 光电二极管（PD）+ 厂商 MCU」构成的模块。

| 项目 | 参数 |
|---|---|
| 测量原理 | 光学（LED 发光 → 弹性体反射 → PD 接收 → AFE 转换） |
| 输出通道 | **3 路 PD**（PD1 / PD2 / PD3） |
| 接口 | UART，**115200 8N1**，3.3V TTL |
| 引脚 | 4 pin：`3V3` / `TXD` / `RXD` / `GND` |
| 协议 | 行文本协议（厂商自定义） |

**为什么用光学方案**：光学测量是**非接触式**的，力敏元件与果皮之间没有直接接触，
避免了传统应变片式传感器在贴合果皮时的应力集中问题。

### 4.2 问题描述

**现象**：

| 工具 | 结果 |
|---|---|
| 厂商上位机 **PS01Tool** | ✅ 正常采集，波形稳定 |
| 自写 **pyserial** 程序 | ❌ 发送同样的字节 `gnst\r\n`，**传感器完全无响应** |

**关键困难**：

- 同一台电脑、同一个 CH340、同一个串口、同一串字节
- **PS01Tool 成功，pyserial 失败**
- 串口抓包工具（Device Monitoring Studio）显示发出的 TX 数据为 `67 6E 73 74 0D 0A`
  （即 `gnst\r\n`，**与 pyserial 发送的完全一致**）

这构成了一个典型的"**同样输入、不同结果**"悖论，说明问题出在被观测系统之外 ——
即**抓包工具本身丢失了信息**。

### 4.3 排查过程

在找到根因之前，系统性排除了以下所有可能性：

| 序号 | 尝试 | 结果 | 排除的原因 |
|---|---|---|---|
| 1 | 命令变体：`gnst\r\n` / `gnst` / `gnst\r` / `gnst\n` | ❌ | 行结束符差异 |
| 2 | DTR / RTS 四种组合 | ❌ | 流控信号 |
| 3 | 发送后延迟 0~5 秒 | ❌ | 时序问题 |
| 4 | 重试 2 / 3 / 5 次 | ❌ | 命令丢失 |
| 5 | 先发 `gned` 再发 `gnst` | ❌ | 状态机残留 |
| 6 | 清空输入缓冲 | ❌ | 缓冲污染 |
| 7 | 多线程持续读取（模仿 PS01Tool 的 SerialWorker 结构） | ❌ | 读线程阻塞 |
| 8 | Windows 与 Linux 双平台验证 | ❌ | 操作系统差异 |
| 9 | 改用 K1 的 40Pin 硬件 UART（`/dev/ttyS10`） | ❌ | USB 转接问题 |
| 10 | 波特率扫描（8 个候选值） | ❌ | 波特率不匹配 |

**同时验证了硬件链路本身是健康的：**

- UART 回环测试：`/dev/ttyS10` 自发自收 **3/3 通过**
- CH340 回环测试：在 K1 上 **3/3 通过**
- 因此排除"串口控制器故障"和"USB 转接故障"

> **方法论提示**：回环测试能证明 **UART 控制器** 正常，但**不能**检测波特率误差
> —— 因为 TX 和 RX 共用同一个时钟源，波特率错了也会"自洽"。

### 4.4 突破口：反编译厂商上位机

当黑盒行为无法用抓包解释时，**反编译上位机成为决定性手段**。

**操作步骤：**

```bash
# 1. 确认 PS01Tool.exe 是 PyInstaller 打包的 Python 3.9 程序
#    （Python 3.14 无法解析 3.9 的 marshal 格式，必须装对应版本）
# 2. 安装 Python 3.9
# 3. 安装解包工具
pip install pyinstxtractor-ng

# 4. 解包
py -3.9 -m pyinstxtractor_ng ps01tool.exe
#    → 得到 PS01Tool.pyc（35,261 字节）

# 5. 尝试反编译（失败）
#    uncompyle6  → "Unsupported Python version, 3.9.0"
#    decompyle3  → 同样的错误（magic number 3425 支持不完整）

# 6. 改用反汇编（成功）
py -3.9 -m xdis.bin.pydisassemble PS01Tool.pyc > PS01Tool_disasm.txt
```

**为什么要换工具**：`uncompyle6` / `decompyle3` 对 Python 3.9.0 的支持不完整，
而 `xdis` 只做**反汇编**（字节码 → 助记符），不依赖版本特定的 AST 还原逻辑，因此更可靠。

### 4.5 根因：隐藏的 `0xD4` 唤醒字节

在反汇编输出中，函数 `send_text_command` 的字节码暴露了真相：

```
124:  20 LOAD_FAST (self)
      22 LOAD_ATTR (serial)
      24 LOAD_METHOD (write)
      26 LOAD_GLOBAL (bytes)
      28 LOAD_CONST (212)          ← ★ 212 = 0xD4
      30 BUILD_LIST 1
      32 CALL_FUNCTION (1 positional)
      34 CALL_METHOD (1 positional)
      36 POP_TOP

125:  38 LOAD_FAST (self)
      40 LOAD_ATTR (serial)
      42 LOAD_METHOD (write)
      44 LOAD_FAST (cmd)
      46 LOAD_CONST ("\r\n")
      48 BINARY_ADD
      50 LOAD_METHOD (encode)
      52 CALL_METHOD (0 positional)
      54 CALL_METHOD (1 positional)
      56 POP_TOP

126:  58 LOAD_GLOBAL (time)
      60 LOAD_METHOD (sleep)
      62 LOAD_CONST (0.02)
      64 CALL_METHOD (1 positional)
      66 POP_TOP
```

**还原为 Python 源码：**

```python
def send_text_command(self, cmd):
    if not (self.serial and self.serial.is_open):
        return False
    try:
        self.serial.write(bytes([212]))              # ← 0xD4 唤醒/同步字节
        self.serial.write((cmd + "\r\n").encode())   # ← 实际命令
        time.sleep(0.02)
        return True
    except Exception as e:
        self.error_signal.emit(f"发送命令失败: {e}")
        return False
```

**结论：**

> 厂商上位机每次发命令都是 **`0xD4` + cmd + `\r\n`**，共 7 字节。
> 其中 **`0xD4` 是传感器固件要求的唤醒/同步字节**，缺失时整包被丢弃。

**为什么抓包工具没发现：**

Device Monitoring Studio 把 `0xD4` 当作**不可打印控制字符**过滤掉了，
只记录了后面的 `67 6E 73 74 0D 0A`（`gnst\r\n`），
因而长期误导排查方向。

> **这是本项目最重要的方法论教训：**
> **抓包工具会过滤控制字符，逆向协议时必须多手段交叉验证。**

### 4.7 数据协议解析

**初始化日志**（约 49~51 行）：以 `[INFO] Data callback registered` 结束，
标志着传感器进入就绪状态。

**数据行格式：**

```
RAW[<索引>]: 0x<AD值 hex> (status=0x<状态 hex>)
```

**通道分配规律：**

| `索引 % 3` | 对应通道 |
|---|---|
| 0 | PD3（子通道 1） |
| 1 | PD2（子通道 2） |
| 2 | PD1（子通道 3） |

**状态行格式**（JSON）：

```json
{"status":"sensor_init","result":1}
{"status":"sensor_state","value":"NORMAL"}
```

### 4.8 接线方案（已验证）

**最终采用方案 —— 单 USB 线：**

```
   PS01 传感器              CH340 模块
   ┌──────────┐            ┌──────────┐
   │  3V3  ●──┼────────────┼── 3V3    │
   │  GND  ●──┼────────────┼── GND    │
   │  TXD  ●──┼────────────┼── RXD    │
   │  RXD  ●──┼────────────┼── TXD    │
   └──────────┘            └────┬─────┘
                                │ USB
                                ▼
                        K1 MUSE Pi Pro（/dev/ttyUSB0）
```

**优点：**

| 优势 | 说明 |
|---|---|
| 一根线解决供电 + 通信 | 无需 40Pin 接线 |
| 电气隔离 | 传感器电源与板卡电源独立 |
| 免配置 | 内核自带 `ch341` 驱动，免驱 |

**为什么不用 40Pin 直连（排除过的方案）：**

| 尝试 | 结果 | 原因分析 |
|---|---|---|
| 传感器由 K1 的 40Pin 3V3（脚 1）供电 | ❌ 无输出 | K1 该引脚电流能力不足以驱动传感器 |
| CH340 由 PC 供电，数据线接 K1 40Pin | ❌ 0 字节 | 跨设备地参考不一致 |

> 注意：K1 的 40Pin UART 本身是健康的（回环 3/3 通过），
> 问题在于**供电能力**和**地参考**，而非 UART 功能。

| 3 | **Python 版本必须匹配** —— PyInstaller 打包的程序需对应版本 Python 解包 | PyInstaller 逆向 |
| 4 | **工具链要有备份** —— `uncompyle6` 失败时用 `xdis` 反汇编兜底 | Python 字节码分析 |
| 5 | **回环测试测不出波特率错误** —— TX/RX 共用时钟，错了也自洽 | UART 调试 |
| 6 | **供电和地参考是隐形杀手** —— 功能正确但电气条件不满足时现象极具误导性 | 嵌入式外设接入 |

## 5. 视觉系统（OV5647）

> **本章是本项目的另一项核心成果。**
> K1 的 MIPI 摄像头走私有框架，标准 V4L2/OpenCV 路径完全不通；
> 通过定位官方 SDK 工具链，最终实现 **13 fps 连续取帧**。

### 5.1 K1 摄像头框架的特点

K1 的摄像头不走标准的 V4L2 "打开设备即可取流" 模型，而是 SpacemiT 的**私有分层框架**：

```
   OV5647 sensor
        │  MIPI CSI-2（2 lane）
        ▼
   ┌──────────┐
   │  CSIPHY  │   d4206000.csiphy
   └────┬─────┘
        ▼
   ┌──────────┐
   │   CCIC   │   摄像头接口控制器
   └────┬─────┘
        ▼
   ┌──────────┐
   │   ISP    │   mars11isp，含 AE/AWB/AF/LTM 等 3A 算法
   └────┬─────┘
        ▼
   ┌──────────┐
   │   CPP    │   后处理（MCTF 降噪等）
   └────┬─────┘
        ▼
   /dev/video6 ~ /dev/video19   （14 个输出节点）
```

**关键特征**：

| 特征 | 后果 |
|---|---|
| 整条链路必须由官方 SDK 建立 | 裸 `cv2.VideoCapture()` 打不开任何节点 |
| ISP 需要固件（firmware） | 需加载 `mars11isp` 固件与 sensor 参数 |
| 拓扑链接默认全部**禁用** | `/dev/media0` 里的 link 需要程序化启用 |
| 输出节点众多（video6~19） | 需确认哪个节点对应哪个通道 |

**媒体拓扑实测**（`media-ctl -p -d /dev/media0`）：

```
v4l-subdev1（sensor0）
      ↓
v4l-subdev21（CSI PHY）
      ↓
v4l-subdev4 / v4l-subdev5（ISP 前端）
      ↓
v4l-subdev8 ~ v4l-subdev17（ISP 处理）
      ↓
video6 ~ video19（最终输出）
```

### 5.4 优化策略：从 0.85 秒/帧到 13 fps

#### 5.4.1 问题

`cam-test` 是**一次性**测试工具，工作方式是：

```
① 建立链路（sensor 上电 → CSI → ISP 固件加载 → CPP 初始化）
② 采集 N 帧
③ 保存一帧到文件
④ 关闭链路，进程退出
```

**问题在第 ④ 步**：进程一退出，链路就销毁。因此：

- 每采一帧都要重建整条链路
- 实测单次耗时 **0.855 秒**（即 **1.2 fps**）
- 无法用于实时视觉

#### 5.4.2 优化一：精简采集帧数

**措施**：通过配置 JSON 的 `test_frame` / `dump_one_frame` 参数，
把"采 500 帧、存第 250 帧"改为"**采 8 帧、存第 3 帧**"。

```python
cfg["test_frame"] = 8
cfg["dump_one_frame"] = 3
```

**效果**：单次采集稳定在 **0.85 秒**（瓶颈转为链路建立开销，而非采集帧数）。

#### 5.4.3 优化二：交互模式保持链路常开 ★

**关键发现**：`cam-test` 支持**交互模式** —— 把 `auto_run` 设为 `0`，程序不会自动采集退出，
而是进入命令行交互，**链路保持开启**。

| 按键 | 作用 |
|---|---|
| `s` | 开始推流（进入 15.6 fps 内部采集） |
| `d` | **保存当前帧**到 NV12 文件 |
| `r` | 保存一帧 RAW |
| `c` | 停止推流 |
| `q` | 退出 |

**实测验证**（连续按两次 `d`）：

```

I: single_pipeline_online_test(1596): "sensor stream on"
I: cpp_client_receive_mctf_buffers(1833): "CPP0: frameid 1, fps 0.0"

d
I: single_pipeline_online_test(1611): "dump one frame"
I: image_buffer_save(211): "save img fileName /tmp/cpp0_output_1920x1080_s1920.nv12"

d
I: single_pipeline_online_test(1611): "dump one frame"
I: image_buffer_save(211): "save img fileName /tmp/cpp0_output_1920x1080_s1920.nv12"
```

**每次按下 `d` 都立刻落盘一帧，而链路始终开启。**

#### 5.4.4 优化三：pty 伪终端解决缓冲问题

**Python 封装时遇到的坑**：

用 `subprocess.Popen(..., stdout=PIPE)` 启动 `cam-test` 后，
程序**永远等不到** `Input a character:` 提示。

**原因**：C 标准库的缓冲策略依赖输出目标类型：

| 输出目标 | 缓冲模式 | 后果 |
|---|---|---|
| **终端（tty）** | 行缓冲 | 每行立即输出 ✅ |
| **管道（pipe）** | **全缓冲**（4 KB 一块） | 日志卡在缓冲区，读不到 ❌ |

**解决方案：用 pty（伪终端）启动子进程**，让它认为自己在终端上：

```python
import pty, os, subprocess

master, slave = pty.openpty()
proc = subprocess.Popen(cmd, stdin=slave, stdout=slave,
                        stderr=slave, close_fds=True)
os.close(slave)
# 之后从 master 读输出、向 master 写按键
```

**同时解决了输入问题**：按键通过 `os.write(master, b"s\n")` 发送。

### 5.5 葡萄识别算法

**策略**：HSV 颜色分割 + 凸包几何判定

**为什么不用深度学习（当前阶段）**：

| 方案 | 优点 | 缺点 |
|---|---|---|
| **HSV + 几何** | 快、无需模型、**判定依据可解释** | 受光照/白平衡影响 |
| YOLO + NPU | 鲁棒、契合"AI 算力"评分点 | 需模型训练/转换 |

**当前采用 HSV + 几何**，用于快速打通"视觉 → 坐标"链路；
NPU 方案作为后续升级方向（详见 §6 优化策略）。

#### 5.5.1 处理流程

```
输入 BGR 帧（1920×1080）
    │
    ├─ ① 降采样到 960×540        ← 性能优化（4 倍加速）
    │
    ├─ ② 灰世界白平衡校正         ← 抗白平衡漂移
    │
    ├─ ③ BGR → HSV
    │
    ├─ ④ 颜色阈值分割（inRange）
    │
    ├─ ⑤ 形态学：开运算去噪 → 大核闭运算填平表面花纹
    │
    ├─ ⑥ 轮廓提取（只处理最大 20 个）
    │
    ├─ ⑦ 几何判定（凸包）
    │      ├─ 圆度 circularity ≥ 0.60
    │      ├─ 实心度 solidity   ≥ 0.72
    │      └─ 面积在 [min_area, max_area] 区间
    │
    └─ ⑧ 按面积排序，最大者为抓取目标 → 输出中心坐标 + 半径
```

#### 5.5.2 关键设计：凸包几何判定

**问题**：真实物体表面往往有花纹、文字、反光、遮挡，导致颜色掩码被切碎，
直接计算轮廓圆度会失败。

**实例**（用彩虹糖盒测试，表面印有文字和图案）：

```
原始轮廓圆度 = 0.29 ~ 0.39   → 判定失败 ❌
```

**解决方案**：改用**凸包（convex hull）**上的几何指标：

| 指标 | 定义 | 球体典型值 |
|---|---|---|
| **圆度** circularity | 4π·A_hull / P_hull² | ≈ 0.85 |
| **实心度** solidity | A_contour / A_hull | ≈ 0.95 |

**凸包的作用**：忽略表面凹坑，只保留整体外轮廓 ——
这样物体表面有花纹、反光、局部遮挡时也不会被误杀。

**双重过滤的效果**：

| 场景 | 圆度 | 实心度 | 判定 |
|---|---|---|---|
| 葡萄 / 球形物体 | 高 | 高 | ✅ 接受 |
| 墙面色块 | 低 | 低 | ❌ 拒绝 |
| 阴影 | 低 | 低 | ❌ 拒绝 |
| 长条形物体 | 低 | 高 | ❌ 拒绝 |

#### 5.5.3 抗白平衡漂移

**问题发现**：

K1 的 ISP **没有加载调参文件**，日志持续出现：

```
I: _ISP_PIPELINE_LoadFwSettingFile(495): "no isp setting file,
                                          use settings from user or sensor!"
```

**后果**：自动白平衡**不稳定** —— 同一场景在不同时刻拍摄，颜色明显漂移。

**实测证据**：米黄色窗帘在一次拍摄中变成了**粉色**，导致：
- 白色墙壁被判定为"红色目标"
- 基于固定 HSV 阈值的检测完全失效

**解决方案：灰世界白平衡校正（Gray-World AWB）**

原理：假设画面整体平均颜色应为中性灰，据此将三个通道拉平。

```python
def gray_world_awb(bgr, strength=1.0):
    f = bgr.astype(np.float32)
    means = f.reshape(-1, 3).mean(axis=0)      # B, G, R 三通道均值
    gray = means.mean()
    for i in range(3):
        gain = gray / max(means[i], 1.0)
        gain = 1.0 + (gain - 1.0) * strength   # 按强度插值
        f[:, :, i] *= gain
    return np.clip(f, 0, 255).astype(np.uint8)
```

**效果**：

| 指标 | 校正前 | 校正后 |
|---|---|---|
| 误检数量（场景中无目标） | 3~4 个假目标 | **0 个** ✅ |
| 掩码质量 | 大片背景被误判 | 干净 |

#### 5.5.4 优化策略汇总

| 优化项 | 措施 | 效果 |
|---|---|---|
| **降采样** | 1920×1080 → 960×540 | 处理耗时 **721 ms → 90 ms**（8 倍） |
| **限制轮廓数** | 只处理最大的 20 个 | 避免大面积噪声拖慢 |
| **减小形态学核** | 闭运算核 15 → 11，迭代 2 → 1 | 进一步提速 |
| **凸包判定** | 用凸包代替原始轮廓 | 表面有花纹也能识别 |
| **灰世界 AWB** | 检测前做白平衡校正 | 误检 3~4 个 → **0 个** |

**综合性能**：

| 环节 | 耗时 |
|---|---|
| 摄像头取帧（`d` 命令 → 落盘 → 读入） | ~77 ms |
| 图像转换（NV12 → BGR） | 包含在内 |
| 葡萄检测（含 AWB + 分割 + 几何） | ~90 ms |
| **合计** | **约 170 ms（≈ 6 fps 端到端）** |

## 6. 力闭环抓取控制

### 6.1 葡萄力学模型

**目标对象**：巨峰葡萄

| 参数 | 数值 | 来源 |
|---|---|---|
| 单颗质量 m | ≈ 12 g | 实测 |
| 赤道直径 d | ≈ 22 mm | 实测 |
| **果皮破裂力 F_break** | **1 ~ 3 N** | 拇指食指挤压实验 |
| 重力 G = mg | 0.12 N | 计算 |

**关键洞察**：

> 葡萄的破裂发生在 **1~3 N**，而吊起它只需要克服 **0.12 N** 的重力。
> 因此任务的核心不是"产生足够大的力"，而是"**把力精确控制在很小的水平上**"。

**摩擦模型**：

夹爪与葡萄之间靠摩擦力承载重力：

```
F_friction_total = 2 × F_clamp × μ
```

| 参数 | 取值 |
|---|---|
| 单侧夹持力 F_clamp | **0.8 N**（目标值） |
| 硅胶垫摩擦系数 μ | ≈ 1.0（邵氏 A30 硅胶 / 葡萄表皮，湿态取 0.7） |
| 总摩擦力 | 0.8 × 2 × 1.0 = **1.6 N** |
| 安全系数 | 1.6 N / 0.12 N = **13 倍** |

**设计裕度**：

| 裕度 | 数值 | 说明 |
|---|---|---|
| 相对破裂力 | 1~3 N / 0.8 N = **1.25~3.75 倍** | 不会压破 |
| 相对重力 | **13 倍** | 不会滑落 |

### 6.2 控制律设计

#### 6.2.1 总体结构

```
                                              ┌──────────────┐
   F*（目标力）───▶⊕───▶ ┌──────────┐  期望速度 ┌─────────┐  位置增量 ┌─────────┐
                   ▲     │ PI 控制器│─────────▶│ 速率限幅│─────────▶│位置累加器│
                   │     └──────────┘          └─────────┘          └────┬────┘
                   │                                                     │
              力误差 e = F* - F                                          ▼
                   │                                              ┌─────────────┐
                   │                                              │ 舵机 PWM    │
                   │                                              │ 50Hz        │
                   │                                              └──────┬──────┘
                   │                                                     │
                   │              ┌──────────────┐                       │
                   └──────────────│ 滑动平均+中值 │◀──── 力采样 ──────────┘
                                  │   双重滤波    │      (135 Hz)
                                  └──────────────┘
```

#### 6.2.2 为什么用"力 → 速度 → 位置"三级结构

**直接用力控制位置会出问题**：舵机是位置伺服器件，无法直接输出指定力矩。
因此采用**级联结构**：

| 级 | 输入 | 输出 | 作用 |
|---|---|---|---|
| **PI 控制器** | 力误差 e | 期望闭合速度（度/秒） | 把力误差转换为速度指令 |
| **速率限幅** | 期望速度 | 受限速度 | **防止冲击过冲** |
| **位置累加器** | 速度 | 角度增量 | 积分成舵机位置指令 |

**核心安全机制是"速率限幅"**：

> 即使 PI 控制器输出很大的速度指令，`force_ramp_n_per_s` 也会把它限制住，
> 保证力是**缓慢爬升**而不是**一步到位**。
> 这是防止冲击压破葡萄的**第一道也是最重要的一道防线**。

#### 6.2.3 PI 参数

```yaml
# 输出是"期望的闭合速度"，单位 度/秒
kp_deg_per_s_per_n: 60.0        # 比例增益
ki_deg_per_s_per_n_s: 40.0      # 积分增益
integral_limit: 30.0            # 抗积分饱和限幅
```

**抗积分饱和的必要性**：接触前力长期为 0，误差恒为 F\*，
积分项会累积到很大值；一旦接触，巨大的积分量会导致力瞬间冲过目标值。
限幅 `integral_limit` 把积分贡献限制在合理范围。

#### 6.2.4 分段控制策略

| 阶段 | 控制方式 | 速率限制 | 目的 |
|---|---|---|---|
| **APPROACH** | 纯位置控制（力开环） | `approach_rate_deg_per_s: 60` | 快速接近，无接触 |
| **CONTACT** | 停止并确认 | — | 需连续 5 次采样超阈值才算接触（去抖） |
| **RAMP** | **力闭环 PI** | `force_ramp_n_per_s: 1.5` | 限速升力至目标 |
| **HOLD** | 力闭环维持 | 容差 `hold_tolerance_n: 0.15` | 模拟搬运 |
| **RELEASE** | 位置控制反开 | `release_rate_deg_per_s: 120` | 快速释放 |

**接触判定阈值**：`force_approach_n: 0.25`（超过它认为已接触）

### 6.3 安全保护层

安全层**独立于控制层**，任何一条触发立即急停 —— 即使控制逻辑本身有 bug，
安全层仍然有效。

| # | 保护 | 触发条件 | 动作 | 参数 |
|---|---|---|---|---|
| 1 | **超力保护** | F > 1.5 N | 立即反向松开 20° | `force_max_n: 1.5`<br>`release_backoff_deg: 20` |
| 2 | **失稳保护** | 实际力上升速率 < 期望速率 × 0.2，持续 1.5 s | 判定滑移，停机 | `slip_ratio_threshold: 0.2`<br>`slip_detect_window_s: 1.5` |
| 3 | **心跳超时** | 主循环卡顿 > 0.5 s | 舵机卸力 | `heartbeat_timeout_s: 0.5` |
| 4 | **阶段超时** | APPROACH > 8 s / HOLD > 10 s | 转入 ABORT | `timeout_approach_s: 8`<br>`timeout_hold_s: 10` |

**失稳保护的物理含义**：

正常夹持时，力应当随位置指令线性上升。如果**力上升很慢甚至停滞**，
说明葡萄在夹爪之间**滑移**（没有形成有效夹持）—— 此时继续加力是危险的，
应当立即停止并报警。

### 6.4 舵机参数与标定

**MG996R 数据手册标称**：0° → 500 µs，180° → 2500 µs，周期 20 ms。

**因此测试脚本采用保守值**：

```python
PULSE_MIN_US = 600      # 比手册的 500 更保守
PULSE_MAX_US = 2400     # 比手册的 2500 更保守
```

### 9.5 常见问题排查

#### 9.5.1 力传感器无响应

**排查顺序：**

| 步骤 | 检查 | 命令 / 方法 |
|---|---|---|
| 1 | 设备节点是否存在 | `ls /dev/ttyUSB*` |
| 2 | 是否被其他程序占用 | `sudo lsof /dev/ttyUSB0` |
| 3 | 接线是否交叉（TX↔RX） | 目视检查 |
| 4 | **启动命令是否含 `0xD4`** | `grep DEFAULT_START_COMMAND scripts/ps01_driver.py` |
| 5 | CH340 回环是否正常 | 短接 CH340 的 TX/RX，用 `scripts/uart_loopback.py` |
| 6 | 传感器供电电压 | 万用表量 CH340 的 3V3 输出 |

**最常见原因**：**启动命令漏了 `0xD4` 字节** —— 这是本项目的核心发现，
详见 §4.5。

#### 9.5.2 摄像头无输出

| 步骤 | 检查 | 命令 |
|---|---|---|
| 1 | sensor 是否被探测到 | `sudo dmesg \| grep -i "sensor.*probed"` |
| 2 | FPC 是否插在 **CAMERA** 座子 | 目视 |
| 3 | 自动配置文件是否生成 | `ls /usr/share/camera_json/csi*_camera_auto.json` |
| 4 | 配置里的 sensor_name | `grep sensor_name /usr/share/camera_json/csi1_camera_auto.json` |
| 5 | 是否有 `Input a character:` 提示 | 手动运行 `sudo cam-test /tmp/interactive.json` |

**最常见原因**：

1. **配置里没用 `ov5647_spm`** —— 必须先用 `csi1_camera_detect.json` 自动探测
2. **用管道而非 pty 启动** —— C 程序缓冲导致读不到交互提示（详见 §5.4.4）

#### 9.5.3 识别误检严重

| 现象 | 原因 | 处理 |
|---|---|---|
| 背景被误判为目标 | 白平衡漂移 | 确认 `--awb 1.0`（默认已开） |
| 目标被漏检 | 圆度/实心度阈值过高 | 降低 `--min-circularity` / `--min-solidity` |
| 检测太慢 | 分辨率过高 | 降低 `--scale`（如 0.35） |
| 目标边缘破碎 | 表面花纹/反光 | 增大 `--close-kernel` |

#### 9.5.4 舵机不转或抖动

| 现象 | 原因 | 处理 |
|---|---|---|
| 完全不转 | 未共地 | 检查舵机电源 GND 与 K1 GND 是否相连 |
| 完全不转 | 信号脚选错 | 用 `--probe` 逐个引脚试 |
| 持续抖动 | 软件 PWM 抖动大 | 改用 PCA9685 硬件 PWM 模块 |
| 发烫 + 嗡嗡响 | 脉宽超出行程，顶死 | 立即断电，缩小脉宽范围 |
| 板子重启 | 舵机从板子取电 | 检查红线，必须接独立电源 |
